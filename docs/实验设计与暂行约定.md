## 1. 目标与待回答的问题

针对 Lean 4 谓词，研究能否自动生成并判断恒真、恒假和逐参数语义独立性目标，同时处理非递归调用。保留两条路线：

- **自动证明路线**：构造 Lean 命题，尝试由 Lean tactic 完成证明。
- **符号执行 + SMT 路线**：分析表达式与调用，形成 SMT 查询或调用现有 Lean-to-SMT 工具，并解释其结果。第一阶段先调查已有转换工具能否覆盖需求，再决定是否自行实现可观察的符号执行过程。

实验首先回答：

1. 能否在 Lean 内读取声明和参数，并自动构造正确的目标？
2. Lean 原生证明、Lean-blaster、Lean-SMT 对相同目标分别取得什么结果？
3. 转换后是否保留真实的函数定义、类型与分支语义？能否查看 SMT 查询和模型？
4. `lean4export` 输出是否足以供外部分析使用，其解析成本如何？
5. 是否真的需要自定义 IR、单独的符号执行器和函数摘要？

第一版不要求保存 Lean 证明证书或重建 SMT 证明；Lean 检查成功、SMT 结果及启发式诊断必须分别标注。工具可能超时或不支持，不保证所有输入均有结论。

## 2. 不依赖具体工具的性质约定

对 `P(x₀,…,xₙ)`，固定全部非目标参数，考察一个参数取不同值时谓词的真假：

| 属性 | 要求成立的命题 | 反例 |
| --- | --- | --- |
| `always_true` | `∀ x, P(x)` | 一组使 `P` 为假的输入 |
| `always_false` | `∀ x, ¬ P(x)` | 一组使 `P` 为真的输入 |
| `independent(i)` | 对固定的其他参数和任意 `u,v`，有 `P(...,u,...) ↔ P(...,v,...)` | 其他参数相同，目标参数两次取值使真假不同 |

首批实验只检查各参数整个类型范围，不添加用户前提；输入类型为 `Int`、`Nat`、`Bool`。对 `n` 个参数，生成 `n+2` 个目标；零参数生成两个恒值目标。`always_true` 和 `always_false` 都被反例推翻，才意味着谓词既有真值也有假值。结论必须指明范围，不推断用户意图。

恒真蕴含所有参数独立，但如果某后端只证明恒真、未单独求解独立性，应记录是**派生结论**，不能当作该后端完成了所有逐参数目标。基准计分先统计逐目标直接结果，再另行统计逻辑派生结果。

## 3. 初期实验输入与基准答案

先使用透明、非递归、一阶、无依赖参数的 Lean 定义；主要测试整数线性算术、逻辑连接、基础分支、非递归调用。`Nat`、`Bool` 和 `let` 作为专项探针，能否纳入第一版最终支持范围由实验确定。递归、高阶、不可展开或依赖类型放在拒绝/未知测试中，不能在未验证前宣称已支持。

### 3.1 主案例

```lean
def gate (mode value noise : Int) : Prop :=
  mode = 0 ∨ value + 2 * noise - noise - noise = 7

def caller (a b c : Int) : Prop :=
  gate ((a + b) + (a - b) - 2 * a) (a + b) c
```

预期答案按请求真假列出：

| 定义 | `always_true` | `always_false` | 参数独立性 |
| --- | --- | --- | --- |
| `gate` | 假 | 假 | `mode` 假；`value` 假；`noise` 真 |
| `caller` | 真 | 假 | `a`、`b`、`c` 均真 |

`gate` 见证：固定 `value=0, noise=0`，`mode=0` 为真而 `mode=1` 为假；固定 `mode=1, noise=0`，`value=7` 为真而 `value=0` 为假。`caller` 任意输入均为真，如 `(0,0,0)` 可推翻 `always_false`。预期是数学真值，不表示所有工具必须找到反例或导出证明。

### 3.2 对照与边界测试

除主案例外，准备固定源文件及人工核对答案：

| 编号 | 测试目的 | 示例及预期 |
| --- | --- | --- |
| C1 | 恒假 | `p(x) := x < x`；`always_false` 真，参数独立 |
| C2 | 非恒值且确实有影响 | `p(x) := x = 7`；恒真、恒假均假，参数独立性假 |
| C3 | 表面使用但恒等消去 | `p(x,y) := x + y - y = 0`；只独立于 `y` |
| C4 | 非退化调用对照 | `q(a) := gate 1 a 0`；等价于 `a = 7`，不恒真、`a` 有影响 |
| C5 | 多层调用 | `h(x) := x + 1`，`p(x) := h(h(x)) = 2`；等价于 `x=0` |
| C6 | 分支 | `p(x) := (if x > 0 then x else 0) = 0`；不恒定且 `x` 有影响 |
| C7 | 自然数截断减法 | `p(n) := n - 1 = 0`，类型为 `Nat`；`n=0` 时真、`n=2` 时假 |
| C8 | 布尔参数 | `p(b) := b = true`；不恒定且 `b` 有影响 |
| C9 | `let` 和遮蔽 | 定义内部使用局部 `let` 且名字与外部变量可区分；与手写展开结果一致 |
| C10 | 拒绝及未知 | 递归、`opaque`、不支持的类型或操作；不得因部分翻译给出确定结论 |

另增加**语义敏感探针**：调用同一函数两次、共享参数约束、负数和大整数、分支两侧均可达、不可满足的查询、超时、模型缺失与语法错误。具体 Lean 源码与答案随实验固定，所有人工答案应由独立手写证明或具体见证复核。

## 4. 实验组与工具入口

实验对象是同一组逻辑目标；不把不同工具特定的空洞性诊断当作同一目标。

| 组别 | 候选 | 正确入口 / 输入 | 需要观察 |
| --- | --- | --- | --- |
| A | Lean 原生 Meta API + tactic | 项目环境中生成 Lean 目标；依次尝试指定 tactic | 能否自动提取参数并证明；失败、超时分开记录 |
| B | Lean-blaster | 针对生成的 Lean 命题使用 `#blaster` 或其文档支持的入口；试正常及 `only-smt-lib` / dump 模式 | 目标结果、原始输出、查询是否生成、函数语义和模型 |
| C | Lean-SMT | 在 Lean 中对相同目标调用其 `smt` tactic | 成功、遗留目标、错误、版本及能否取得查询/反例 |
| D | lean4export | 在匹配项目的 Lean 环境导出指定声明及所需依赖 | 实际 NDJSON 的定义、表达式、引用和函数体，导出成本 |
| E | 直接手写 SMT-LIB + 求解器 | 按基准性质独立手工编码，仅作参照 | 求解器是否能处理问题及提供见证；不计为 Lean 转换正确 |
| F | 符号执行路线候选实现 | 首先考察已有工具能否提供所需符号状态、分支和调用处理；不足时评估独立原型 | 路径/分支、调用与模型可观察性；与现有转换器对照 |

Lean-blaster 可能在优化阶段直接得到结果而不生成 SMT 文件；记录为 `optimized_before_smt`，不能因此当作已经观察到 SMT 翻译。其文档说明不重建完整证明，tactic 使用 `admit` 的成功结果不得标记为 Lean 内核完整证明。Lean-SMT 有可能留下证明义务，只有目标无遗留且无 `sorry` 才记为 Lean 证明完成。两条路线分别调度不代表技术独立：Lean-SMT 内部本身使用 SMT。

可选扩展基线：ATP-Checkers 和 Anchor 应按其各自支持的声明入口执行，作为**专项检测结果**单列；其“未发现”不能等价于目标已证明。Lean REPL、Pantograph、LeanDojo、lean-extract 是交互、源码追踪或数据提取候选，不应把其 JSON 默认视为可直接供符号执行的已 elaboration 表达式。必要时再进行接口测试。

## 5. 执行步骤

### 阶段 0：环境及版本盘点

记录操作系统、项目根、Lean/Lake、项目依赖、各工具仓库提交、求解器版本与完整运行参数。项目工具链与插件不兼容时，使用独立的实验工程和兼容版本分别测试，保留相同源案例；不能悄悄改写目标项目版本。记录兼容性问题。

目前工作区内存在 Lean 4.27.0-rc1 和 4.30.0-rc2 及先前案例；`gate/caller` 的手写目标在 4.27.0-rc1 下曾成功验证。该版本不是产品固定版本。之前命令环境没有发现 `z3`、`cvc5`；具体安装状态须在实验时重新检查。Lean-blaster、Lean-SMT 和 lean4export 尚未在本实验中运行。

### 阶段 1：建立参考答案与正负对照

整理独立 Lean 测试模块，保持分析案例与手写证明/具体见证分文件。手写证明运行时检查失败和 `sorry`；具体见证确认预期真假。控制台输出、版本和完整命令写入结果。手写目标的成功不计为“自动生成目标成功”。

### 阶段 2：Lean 内目标生成

从真实 Lean 环境中读取目标声明；构造每种命题，记录实际生成的 Lean 目标。对 `gate` 检查目标参数确实是第三个、另外两个共享；对 `caller` 检查定义引用和实际实参。自动生成的目标应与手写参考目标逐项对应，可由 Lean 中的等价性检查或逐案审查验证；生成目标本身不能改变语义。

### 阶段 3：工具调用与输出保留

针对每个目标分别调用 A、B、C；D 分别导出 `gate`、`caller` 及依赖；E 使用独立人工编码。实际目标、命令、输出、超时、退出码和产生的 `.smt2` 都要保留。SMT 模型要映射回参数，并用 Lean 原始定义或独立求值重放；仅 IR 重放只能证明其与 IR 一致，不证明翻译一致。

对 B、C 检查 `gate` 函数体是否展开或以有约束的定义保留。若只出现没有语义约束的未解释 `gate`，记录为“原定义语义未确认”，不能把求解结论当作原 Lean 谓词的确定结论。未生成查询时记不可观察，不猜测内部编码。

### 阶段 4：比较、定位分歧、决定设计

先比较每个目标与参考答案，再比较覆盖率与耗时。遇到结果冲突、`sorry`、不完整目标、生成目标不一致或模型重放失败，应保留原始输出，定位目标、翻译及调用；冲突不投票、不自动选边。版本或环境导致无法运行计为 `not_run`，不算分析失败或语义不支持。

## 6. 结果状态和证据约定

每条记录同时保留标准状态和工具原始结果；状态相对于请求性质：

| 状态 | 含义 |
| --- | --- |
| `confirmed` | 有充分的该后端成功结果；注明 Lean 检查或 SMT 条件性结论 |
| `refuted` | 找到并验证了相应反例；注明验证依据 |
| `candidate` | 工具报告反例或结论，但模型、翻译或目标对应性尚未核查 |
| `unknown` | 策略未完成、求解器未知或超时 |
| `unsupported` | 工具明确拒绝该输入/表达式或超出其明确支持范围 |
| `error` | 进程、解析、环境或内部错误 |
| `not_run` | 因依赖、版本、成本或环境未执行 |

Lean `sorry` / `admit` 或遗留证明目标不是完整 Lean 证明。SMT `unsat` 仅在查询正确编码且覆盖对应范围时作为条件性 `confirmed`；与原 Lean 目标的对应性没有核实前应标为 `candidate`。`sat` 模型只有在重放后才可作为 `refuted`。没有反例不等于 `unsat`，策略失败不等于性质为假。参考答案与工具输出冲突，作为异常单独记录。

实验记录最少包括：案例和目标 ID、目标文本及参数映射、工具/版本/环境、入口及命令、时间与限制、原始状态、标准状态、证据类型、见证及验证结果、原始产物路径、目标和翻译核查状态、备注。字段可用 CSV/JSONL 暂存；这不是最终产品接口或通用 Lean IR。

## 7. 产物与复现约定

每次实验独立保存，建议目录：

```text
experiments/<run-id>/
  manifest.json         # 工具版本、提交、项目、环境、命令和限制
  cases/                # 案例与参考答案的版本或副本
  goals/                # 实际提交的 Lean 目标
  exports/              # 导出的原始 NDJSON / 其他格式
  queries/              # 实际获取的 SMT-LIB，未产生则说明原因
  logs/                 # stdout、stderr、退出码及耗时
  results.jsonl         # 每个案例 × 目标 × 工具一条
  report.md             # 比较、错误与未完成项
```

路径、文件名和记录格式均为实验约定，可根据工具适配调整。实验不修改原始案例或目标项目；允许创建隔离的临时文件与独立工程。固定每次的超时和资源预算并记录；目前尚不预设产品默认超时。可重复检查结果与执行过程，不把同一进程中状态污染或缓存命中误当成独立验证。

## 8. 比较指标与决策标准

- **目标生成正确率**：自动目标与基准的对应情况，单独计数；无正确目标不纳入求解成功。
- **覆盖**：各属性的 `confirmed`、`refuted`、`candidate`、`unknown`、`unsupported`、`error` 和 `not_run` 分开统计。
- **语义一致性**：与手写证明、Lean 重放及独立人工编码的对照是否一致；差异必须解释。
- **调用能力**：多层定义、重复调用、分支和 `Nat` 是否准确；记录是展开、定义保留、未解释还是不可观察。
- **可观察性**：能否保留目标、查询、模型及对应源位置；优化阶段结束时需标明没有 SMT 查询。
- **代价**：安装和版本兼容、分析时间、依赖与维护成本；比较时分别记录冷启动及复用环境的条件。

选择顺序：若已有工具在目标子集上通过语义与调用测试，并能提供符号执行路线所需的符号状态、分支和调用处理，优先复用；若只能完成 Lean-to-SMT 转换而缺少所需的过程能力，则补充实现或选择可提供这些能力的工具，以完成既定的符号执行路线。若现有工具不支持必要语义，则比较 `lean4export` 与 Lean 内部 API，再决定是否自定义 IR。**不得在实验前假定必须采用自定义 JSON IR，也不得把现有 Lean-to-SMT 转换等同于已完成可观察的符号执行。**
