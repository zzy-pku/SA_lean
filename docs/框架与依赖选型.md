# 第一版框架与依赖选型

日期：2026-11-25
状态：历史选型记录；当前 SMT 原型及实测状态见仓库根目录 README

> **选型修正（2026-11-25）：**此前将两个工具仅列为对照并直接选择自建符号执行模块，证据不足。现调整为优先将 Lean-blaster 和 Lean-SMT 接入并用主案例验证；是否需要独立符号执行模块，由具体能力缺口决定。下文与本修正冲突的描述均以本段及第 1、2 节为准。

## 1. 选型结论

| 职责 | 选用 | 作用与边界 |
| --- | --- | --- |
| Lean 项目加载和分析底座 | Lean 4、Lake、Lean Meta API | 在目标版本的 Lean 环境中读取 `Environment`、声明类型和 `Expr`，实现参数提取与目标生成 |
| 自动证明路线 | Lean 原生 `simp`、`omega`；其他策略按版本可用性接入 | 对自动生成的 Lean 目标尝试证明；失败是未知 |
| 符号执行 + SMT 路线 | 优先使用 Lean-blaster + Z3；评估其符号状态、调用和分支可观察性 | 先复用 Lean 表达式优化及 SMT 转换；若不满足所需符号执行能力再补充模块，不能把现有转换直接称作完整符号执行 |
| SMT 求解 | Z3；手写对照使用已有 Z3 Python 绑定；Lean-blaster 的求解器配置以实际兼容版本为准 | `sat/unsat/unknown` 和模型依赖实际编码，不能默认翻译正确 |
| 进程与实验编排 | Python 标准库 | 调用 Lean 和求解器、资源限制、日志及报告；不是分析算法框架 |
| 自动证明增强及交叉验证 | Lean-SMT + cvc5 | 作为自动证明路线候选后端；是否完整关闭 Lean 目标需逐次检查；不假设与 Lean-blaster 当前版本能在同一工具链中构建 |
| 外部 Lean 导出 | lean4export | 暂不列为主路径依赖；需要外部消费完整 Lean 内核表达式时再测试 |

Lean 端负责消解实际 Lean 环境、绑定、类型与表达式。优先调用现有工具处理 Lean 表达式并构造 SMT 查询，不预先要求自行实现通用 IR 或符号执行器。需自行实现目标生成及结果归一化；如果现有工具不提供所需可观察符号状态、分支路径或调用解释，再依据实测缺口补充模块。Lean 与编排器之间的传输模式待原型验证；Z3 查询能导出时以 SMT-LIB 留档。手写目标和手写 SMT 查询只作基线，不代表自动分析完成。

## 2. 两条路线

```text
Lean 项目 → Lean 环境 / 声明及参数 → 自动目标构造
                        ├─ Lean tactic / Lean-SMT + cvc5：尝试证明目标
                        └─ Lean-blaster + Z3：优化、转换并求解
                              ↓
                   按需补充符号状态、分支与调用分析
                        ↓
               证据、模型和统一诊断
```

符号执行路线要能够处理受支持的调用、参数、`let` 和条件，并满足所需的分支或符号状态可观察性。首先实测 Lean-blaster 已提供的功能；它的转换和优化不自动等价于完整符号执行。资源限制或不支持的表达式不得产生确定结论。需要核查 `Nat` 截断减法、整数、逻辑运算、类型实例及变量绑定的语义。具体支持集在原型测试通过后发布；其他内容返回 `unsupported` 或 `unknown`。

分析目标、结果状态和评估流程以 [实验设计与暂行约定](实验设计与暂行约定.md) 为准；第一版不要求 Lean 证书或 SMT 证明重建。Lean tactic 只有实际证明目标且无 `sorry` 才报告 Lean 证明；Z3 的 `unsat` 是受翻译正确性约束的求解器结论。`sat` 模型应进行原始 Lean 定义验证或标明仅经中间表示重放；不能把未验证模型提升为可靠反例。

## 3. 已有证据

- 工作区本地 Lean `4.27.0-rc1` 可运行；[DependencyCaseProofs.lean](../examples/DependencyCaseProofs.lean) 中人工给定的 `gate` 和 `caller` 目标通过，且 `#print axioms` 未显示 `sorryAx`。这是手写目标实测，不是自动提取或自动生成实测。
- Python 可导入 Z3 `5.4.1`，尽管当时 `PATH` 中无 `z3` 命令。运行 [z3_gate_probe.py](../examples/z3_gate_probe.py) 的手写编码得到 `gate.noise` 反例查询 `unsat`、`gate.mode/value` 反例查询 `sat`、`caller` 假值查询 `unsat`。这验证求解器及数学编码，不验证 Lean 翻译或模型与 Lean 之间的对应。
- Lean-blaster 文档支持直接使用 Lean 命题和 SMT-LIB 导出选项，但其 tactic 文档声明通过 `admit` 处理求解器判定的有效性；不能作为 Lean 内核证明。当前项目尚未安装及运行该工具。[Lean-blaster](https://github.com/input-output-hk/Lean-blaster)
- Lean-SMT 使用 cvc5 并尝试重建 Lean 证明；可能遗留证明目标。当前项目尚未安装及运行该工具。[Lean-SMT](https://github.com/ufmg-smite/lean-smt)
- 检索到的仓库版本文件中，Lean-blaster 使用 Lean 4.24.0，Lean-SMT 当前主分支使用 Lean 4.35.0；这说明不能假设其当前版本相互兼容，也不能假设兼容本地 4.27.0-rc1。最终须固定实际验证的提交和工具链。
- 当前 shell 的 GitHub `git ls-remote` 未成功，返回 `getaddrinfo() thread failed to start`。这不证明远端仓库不可用；本轮未完成工具下载或安装。

## 4. 待验证及依赖管理

1. 开发原型可先用本地 4.27.0-rc1，但它是候选发布版，并非已确定的正式支持版本。先选择与项目兼容的稳定 Lean，实际验证后在 `lean-toolchain` 固定；不自动修改被分析项目工具链。
2. 锁定经端到端测试的 `z3-solver` 包版本及 Python 版本，确认 Windows 和目标平台安装；Python API 不要求系统 `PATH` 中存在独立命令。独立 `z3` 可执行文件另行配置。
3. 选取与各自 Lean 版本匹配的 Lean-blaster 和 Lean-SMT 提交，在独立环境用 `gate/caller` 测实际目标、函数语义、查询与反例；仅在能力不足时补充符号分析模块。尤其测试 `Nat` 截断减法和分支。
4. 检查两个工具在同一 Lean 版本的兼容提交；若不能兼容，以独立可复现环境评估，并明确不能直接分析其他版本编译产物。
5. 检验模型能否映射回源参数以及在原 Lean 定义中重放；失败时保留候选见证并标记未验证。
6. 如依赖安装或版本不兼容导致运行失败，以 `not_run` 报告；不将环境问题视为性质不成立。

## 5. 现阶段不选为必需依赖的理由

Lean REPL/Pantograph 主要提供长进程交互与证明状态管理；第一版先用 Lake/Lean 环境及外部编排即可，性能成为瓶颈再评估。LeanDojo 适合源码 AST、位置与追踪；不能直接视为已 elaboration 语义 IR。Anchor、ATP-Checkers 是专项基线，不提供本项目完整流程。自定义大型 JSON AST、项目全量扫描、函数摘要与抽象解释均不属于本次选型前提。
