# Lean 4 谓词语义依赖与退化分析工具

> **设计更新：**实验和当前有效约定见 [实验设计与暂行约定](实验设计与暂行约定.md)。本文中的接口与实现路线仅为早期方案；不要求自定义表达式 JSON 或预先选定求解器。旧版 [第一版功能与接口约定](第一版功能与接口约定.md) 已归档。

版本：0.1（初步设计）
日期：2026-11-25

## 1. 项目背景

Lean 可以检查证明是否符合形式化陈述，但形式化陈述本身仍可能没有表达预期性质。一个谓词可能恒真、恒假，或在语法上使用某个参数而实际上不受该参数影响。这些情况也可能在调用时出现：被调用谓词本身并不恒真，某个具体调用却因传参或上下文而恒真。

此类现象不一定是缺陷：忽略某个参数可能是有意设计。因此，本工具报告可复核的语义事实和分析依据，不直接断言代码或规范存在错误。

## 2. 项目目标

面向 Lean 4 谓词，自动分析参数语义依赖和谓词退化，分别通过自动证明、符号执行与 SMT 求解给出可追溯的分析结果。

第一版不要求提取、保存 Lean 证明证书，也不要求将 SMT 证明重建为 Lean 证明。Lean 证明成功和 SMT 求解结果的证据性质不同，报告必须保留其来源和限制。

### 2.1 核心问题

设谓词为 `P(x, y)`，固定其他参数时：

1. **参数无影响**：是否对所有 `x`、`y₁`、`y₂`，都有 `P x y₁ ↔ P x y₂`。
2. **参数有影响**：是否存在相同的其他参数和两个该参数的取值，使谓词真假不同。结果应尽可能包含具体见证。
3. **恒真**：是否对所有输入，`P` 均成立。
4. **恒假**：是否对所有输入，`P` 均不成立。
5. **调用上下文退化**：在调用者的实际传参和有效上下文中，是否出现上述现象。

分析目标是有明确作用域的逻辑命题。若后续支持上下文约束，必须同时说明两次参数取值需要满足的约束及其含义，避免将受限结论报告为全局结论。

### 2.2 第一版范围

- 指定待分析定义，而非默认扫描整个项目。
- 非递归、一阶、参数及返回类型不依赖其他参数值的 Lean 4 谓词，返回类型为 `Prop`。
- 优先支持 `Int`、`Nat`、`Bool` 的明确子集，以及基础算术、比较、逻辑运算、条件表达式和非递归定义调用。具体支持运算以实现中的能力表为准。
- 第一阶段通过展开定义处理调用；函数摘要、复杂上下文敏感分析及抽象解释留待评估。
- 对范围外表达式明确报告不支持；超时或无法决定时报告未知。

一般 Lean 命题的这些性质无法保证都能自动判定，第一版不承诺完全覆盖。

## 3. 示例与预期结果

```lean
def gate (mode value noise : Int) : Prop :=
  mode = 0 ∨ value + 2 * noise - noise - noise = 7

def caller (a b c : Int) : Prop :=
  gate ((a + b) + (a - b) - 2 * a) (a + b) c
```

`gate mode value noise` 等价于 `mode = 0 ∨ value = 7`。因此：

- `gate.noise` 无影响；`gate.mode` 和 `gate.value` 有影响。
- `gate` 既非恒真也非恒假。
- `caller` 给 `mode` 传入的表达式恒为零，所以 `caller` 恒真，`a`、`b`、`c` 均无影响。
- `caller` 中 `a` 和 `b` 也出现在传给 `value` 的表达式中；即使 `gate` 全局依赖 `value`，该调用的第一析取支已成立，第二支也不会影响最终结果。

示例见 [DependencyCase.lean](../examples/DependencyCase.lean) 和 [DependencyCaseProofs.lean](../examples/DependencyCaseProofs.lean)。此前在 Lean 4.27.0-rc1 下，人工提供目标和策略后，相关证明通过。当前原型的实现状态以根目录 README 为准。

## 4. 分析路线

### 4.1 路线一：自动证明

从待分析定义生成 Lean 证明目标，并调用 `simp`、`omega`、`grind` 等可用策略。以 `noise` 为例：

```lean
∀ mode value n₁ n₂,
  gate mode value n₁ ↔ gate mode value n₂
```

证明成功表示 Lean 接受了相应目标的证明。策略失败、超时或未覆盖并不表示目标为假。参数有影响可通过构造或搜索见证，再判断具体见证是否成立。

第一版不要求实现证书管理；仍应保存生成的目标、使用的策略、工具版本、执行状态和日志，以便复现。

### 4.2 路线二：符号执行与 SMT

在支持的表达式范围内，使用符号输入执行谓词和非递归调用，构造路径约束及 SMT 查询。

对参数独立性，使用共享其他参数的两次调用，询问是否存在某组输入使两次调用的真假不同：

```text
∃ mode value n₁ n₂,
  gate(mode, value, n₁) ≠ gate(mode, value, n₂)
```

- `sat`：参数有影响；模型是候选见证，应尽可能验证或重放。
- `unsat`：在翻译正确、查询覆盖完整目标范围的前提下，参数无影响。
- `unknown` 或超时：结论未知。

对恒真，检查是否存在使谓词为假的输入；对恒假，检查是否存在使谓词为真的输入。必须记录查询语义及原始求解器状态，不应把未经 Lean 检查的 `unsat` 描述成 Lean 证明。

Lean 表达式到中间表示及 SMT 的翻译是可信边界。尤其要正确处理 `Nat` 截断减法与 `Int` 减法、类型范围、运算和路径条件。对于不能准确建模的构造，返回不支持或未知。

## 5. 系统架构

```text
Lean 项目
   │
   ▼
前端适配器：加载环境，提取声明、类型、表达式及调用关系
   │
   ▼
分析对象：Lean 声明引用 + 后端可用的结构化中间表示
   │
   ▼
目标生成器：恒真、恒假、逐参数独立性
   │
   ▼
统一求解请求
   ├── 自动证明适配器 → Lean 和证明策略
   └── 符号执行适配器 → SMT-LIB → SMT 求解器
   │
   ▼
结果汇总：结论、来源、范围、证据、日志与限制
```

优先复用 Lean 自身的 elaboration、环境与元编程接口，以及现有证明器和 SMT 求解器。尚未确认现有外部工具能直接输出本项目需要的完整表达式格式或自动生成所有目标，因此前端适配和目标生成可能需要自行实现。

自动证明路线可以通过项目、模块和声明名重新加载 Lean 环境；SMT 路线需要能够准确表达受支持 Lean 构造的结构化中间表示。不能仅依赖未说明语义的源码字符串。

## 6. 接口初步设计

以下仅为接口草案，不是已实现的格式。采用版本化 JSON 表达元数据和请求，Lean 目标文件、SMT-LIB 文件及日志作为可复现的独立产物。

### 6.1 分析对象

```json
{
  "schema_version": "0.1",
  "source": {
    "project": "example",
    "module": "Example",
    "declaration": "gate",
    "lean_version": "actual-version"
  },
  "parameters": [
    { "name": "mode", "type": "Int" },
    { "name": "value", "type": "Int" },
    { "name": "noise", "type": "Int" }
  ],
  "return_type": "Prop",
  "body": { "representation": "typed_ir", "value": "..." },
  "calls": []
}
```

结构化中间表示的具体语法、类型规则、定义引用、源码位置、字面量、绑定变量和错误处理需在实现前确定。`value` 在此仅是占位，不是可用表达式。

### 6.2 求解请求

```json
{
  "schema_version": "0.1",
  "request_id": "gate.noise.independence",
  "target": { "module": "Example", "declaration": "gate" },
  "property": { "kind": "parameter_independence", "parameter": "noise" },
  "domain": { "assumptions": [] }
}
```

第一版属性类型为 `parameter_independence`、`predicate_always_true` 和 `predicate_always_false`。请求还需在正式规范中定义参数标识、量化范围、超时、依赖版本和上下文表示。

### 6.3 求解结果

```json
{
  "schema_version": "0.1",
  "request_id": "gate.noise.independence",
  "backend": "smt",
  "status": "confirmed",
  "evidence_kind": "smt_unsat",
  "raw_status": "unsat",
  "witness": null,
  "artifacts": { "query_file": "gate.noise.smt2", "log_file": "gate.noise.log" }
}
```

状态相对于请求中指定的性质解释：

| 状态 | 含义 |
| --- | --- |
| `confirmed` | 当前后端确认请求性质；必须附证据来源 |
| `refuted` | 请求性质被反例推翻；尽可能附见证及其验证状态 |
| `unknown` | 超时、证明搜索未完成或求解器无法决定 |
| `unsupported` | 定义或请求超出后端支持范围 |
| `error` | 工具运行、转换或接口处理出错 |

例如，独立性请求被 `refuted` 对应参数有影响；恒真请求被 `refuted` 只说明存在一个为假的输入，不代表谓词恒假。某工具报告“未发现问题”，不得自动映射为 `confirmed`。

每个适配器应声明支持的输入类型、运算、目标种类和证据类型。应记录工具与版本、资源限制、原始状态、假设、翻译范围及产物路径。同一请求若出现冲突结论，报告分析异常并保留双方证据，不自动选择其中一个。

## 7. 已有工具与复用边界

- **Lean tactic**：人工给定目标时可证明本例；适合作为自动证明后端和直接基线。
- **Lean-SMT / SMT 求解器**：可研究作为后续求解或证明后端；第一版 SMT 路线不要求证明重建。
- **ATP-Checkers**：提供矛盾假设、语法未使用变量等检查；工作区本例直接检查未报告目标结论。
- **Anchor**：支持定理假设和结论审计；本例直接传入带参数定义不符合其入口要求，更合适的定理测试也未自动完成本例恒真目标。它是重要对照，不等同于逐数据参数独立性分析。
- **IronSpec**：Dafny 规范测试已有输入输出依赖及变异过程中的调用路径空洞性分析，是重要相关工作；不能将跨调用退化分析作为一般意义上的空白方向。
- **LeanScreen、Is My Lean Proof Vacuous、LeanFlow/BEq+**：提供部分相关筛查、审计或等价性能力；此前未对所有完整工作流使用合适接口完成实测，不应作全面能力结论。

本项目当前尚未确认有现成工具完整提供目标功能组合；这不是不存在类似工具的证明。新增适配器前应核查官方入口、输入类型、具体语义及版本。

## 8. 第一版实现步骤

1. 固定 Lean 版本和最小支持语言子集，完成项目加载及指定声明提取。
2. 定义并验证带类型的中间表示、分析请求和结果格式。
3. 对简单无调用谓词自动生成三类目标，接通 Lean 自动证明路线。
4. 接通符号表达式翻译与 SMT-LIB 查询，记录原始结果和见证。
5. 支持非递归调用展开，完成 `gate/caller` 示例。
6. 统一展示两条路线的结果、未知项与原始产物；对冲突结果明确标记。
7. 构建测试集并与直接展开加 Lean tactic、直接 SMT 查询等基线比较，再决定是否需要函数摘要。

## 9. 验收与评估

第一版至少覆盖：恒真、恒假、参数确实有影响、语法使用但语义无影响、调用上下文导致恒真或恒假、多层非递归调用、类型与运算边界、超时和不支持情况。对 SMT 模型应检查见证确实满足原始目标条件；对翻译建立与 Lean 语义的针对性一致性测试。

`gate/caller` 的验收结果应包含：`gate.noise` 无影响、`gate.mode` 和 `gate.value` 有影响、`gate` 有真有假；`caller` 恒真且三个参数无影响。已确认结论必须能追溯到后端、查询或证明目标与日志。

评估指标包括：已确认和未知比例、与基准答案的一致性、错误结论、分析耗时、见证生成及验证比例、翻译不支持比例。评估时区分两条路线和证据来源，不将求解失败计为性质不成立。
